# Feature check

Before the schema was written, each feature doc was read against the decisions (D1 to D30), the schema review, and the readiness reviews in PR #5. This page records schema coverage, not release readiness: what each release 1 feature needs from the database, where it lives, and the gaps that are still open. Feature 13 (Physical shop) is release 2 and was checked only to make sure nothing here blocks it.

## Open gaps

These are release requirements, not automatically harmless schema gaps. Their owning tasks must resolve the behavior and add tests before the affected feature ships.

| #   | Gap                                                                                                                   | What the schema does now                                                                                  | Needs                 |
| --- | --------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- | --------------------- |
| 1   | Feature 03's import offers "create a second record" for a phone that already exists, but a phone is unique per store. | The unique index stays; import offers "update existing" or "skip".                                        | Doc fix in feature 03 |
| 2   | The upazila list and Bangla names need an official source (BBS).                                                      | 8 divisions and 64 districts seeded; upazilas come with DB-6.                                             | Task DB-6             |
| 3   | Notification escalation (who gets a push when nobody answers, and when) is not fully specified (F08-11).              | `notifications.dedupe_key` per user, `push_subscriptions` ready.                                          | Rules in feature 10   |
| 4   | Abuse reports for the admin trust and safety queue have no table.                                                     | None. An `abuse_reports` table is additive when the screen is designed.                                   | Admin design          |
| 5   | Admin announcements (banner to all shops) have no table.                                                              | Stored as a `platform_settings` key.                                                                      | None unless they grow |
| 6   | Analytics metric definitions (F08-10).                                                                                | `store_daily_metrics` is one long table keyed by metric name, so the list can change without a migration. | Task ANA-1            |

Closed since the first check: D27 (saving the buyer's own phone, see [isolation-and-access.md](isolation-and-access.md#customer-identity-d26-d27)), D28 (no two-person approval for admin actions) and D29 (keep the 7-day merge undo, table `contact_merges`). Feature 12 no longer mentions an admin database role. From the AI review: photo matching has `products.image_embedding`, every embedding records its model, taught rules can be undone through `ai_rule_changes`, and D30 adds customer memory.

Questions that do not change the schema: Q1 (prices and limits are rows in `plans`), Q2 (WhatsApp BSP), Q7 (Inquiry stays a chat flag), Q8 (models are settings), Q11 (an organisation table is additive), Q13 (variant keys have source/account scope; synchronization and legacy reconciliation remain planned), Q15 (semaphore lives in Valkey).

## Review status

[PR #6 resolution matrix](review-fixes.md) maps the database fixes and remaining service acceptance criteria. The original review inspected every changed file and every table, with no demonstrated application-level N+1 loop. Its measured issue was repeated membership scans in one admin statement. The index change addresses that lookup; batching, cursor stability, tenant-skew plans and realistic payload/load measurements still belong to feature implementation. Passing schema checks cannot prove production throughput, provider behavior, complete erasure or authorization across unimplemented routes.

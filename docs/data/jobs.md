# Jobs

Planned release 1 background jobs: its queue, what starts it, its payload and what makes a second run harmless. The rules are in [jobs.md](../rules/jobs.md); the queues are the nine in [architecture.md](../architecture.md#queues). These contracts guide feature implementation; the schema PR does not implement the handlers. Every payload has `storeId` unless the row says "sweep", and is parsed with a zod schema in the job file.

A store job that loses its Valkey entry is found again by a sweep. Store sweeps call a `SECURITY DEFINER` function from [isolation-and-access.md](isolation-and-access.md) that returns `(store_id, id)` of due work, then queues one job per row. Sweeps run on a BullMQ repeatable schedule in the `sync` queue (or `payments`, `campaign` and `workflow` where marked) and carry no `storeId` themselves.

## Workflow lease and provider handoff

`due_automation_runs` claims waiting work whose wake time passed, or running work whose `claimed_at` is at least five minutes old, and skips runs of a paused workflow. Each claim updates `claimed_at`; it does not count an attempt. The function returns the step and the new `claimed_at`, truncated to milliseconds for lossless JavaScript Date round-trips, and the queue job carries both; a stale worker may neither advance the run nor overwrite a later claim. The sweep reads how many step jobs already wait in the `workflow` queue, outside any transaction, and claims no more than the room left under 1,000, and at most 100 runs of one store, taking stores in turn so one store's backlog cannot hold back the others. It queues one `continue-automation-run` job per claim, deduplicated on run, step and claim time, so a new claim of the same step is never dropped behind an old job.

The step job does nothing unless the run is still `running` on that step with that `claimed_at`. It writes the step row and the run's next state in one transaction whose update is guarded on both. A step that goes straight on sets a fresh `claimed_at` in that transaction, which renews the lease, and queues the next step's job with it; there is no separate heartbeat. The job adds one to `attempts` when it starts work on its claim, and each committed step sets it back to 0, so a lease that expired while the job waited in the queue does not count. `startWork` also writes a fresh `claimed_at`, so a job that starts late works under a full lease. A job that fails before `startWork`, or never runs, is not counted either; its run is claimed again at each lease expiry. The queue does not retry a failed step job, as a retry would no longer hold the claim `startWork` renewed; the lease and the next sweep are the retry. A run whose step job started more than 10 times without a committed step fails. No database lock is held during a vendor call.

Runs of a paused workflow are left out by a `NOT EXISTS` on `automations` for each due row, so they are still read each tick. That is cheap while few workflows pause; an index or a join that drops paused workflows first can come once a store keeps many paused runs.

A crash between claiming and enqueueing is recovered by the next stale-lease sweep. This database behavior is tested; exactly-once external delivery is not established by a unique step row. Send steps record their intent as a `sending` step row before the provider call and resend with the same provider idempotency key (feature 09). Pausing or stopping an old version is checked again before the next step; graph data remains immutable.

## Customer memory

Read a bounded page of new messages after the conversation's `(memory_built_through_message_at, memory_built_through_message_id)` checkpoint. The timestamp survives message retention; the ID breaks ties. One contact may have several independent conversation checkpoints. Read the contact-memory version, conversation memory version, checkpoint and contact ownership before the model call; compare all of them in the final short transaction. A mismatch discards the result and schedules a fresh read. Advance the conversation checkpoint even when the response adds no durable fact, and still update its conversation summary.

Staff edits and model output use `contactMemorySchema`: summary at most 600 characters, at most 40 strict facts, each value at most 160 characters, typed source, source UUID and timestamp, with a 16,384-byte serialized memory limit. The prompt builder selects complete facts and shortens the summary until the rendered context fits both 1,200 UTF-8 bytes and 300 tokens measured by the selected model's tokenizer. If the tokenizer is unavailable, omit memory rather than estimate the token count. Staff facts are not overwritten by model extraction.

Clear empties memory, sets `cleared_at`, increments the contact-memory version and each conversation memory version, and advances every conversation checkpoint to its latest message. New extraction excludes messages and own-order evidence at or before that cutoff; it must not replay old orders into cleared memory. Merge and undo invalidate both memories, preserve correctly owned staff facts and the strictest relevant clear cutoff, and enqueue rebuilds through the outbox. Concurrent or older model writes must fail their guards.

## Metrics and attribution

Order, payment, return and send/tap outbox events schedule bounded summary work that becomes visible within five minutes. Nightly reconciliation recomputes affected days from retained source evidence; it is a repair path, not the only refresh. Late returns and corrections restate the original store-local metric day as defined by ANA-1 and refresh affected totals. ANA-1 implements the order summary handlers and nightly report repair. Marketing attribution handlers follow ANA-2.

Attribution rebuilds cover 365 days plus the maximum seven-day lookback. They read individual `tracked_link_visits`, kept 13 months with exact times ([growth.md](growth.md#link-visits-without-personal-data)). Retain workflow steps for 372 days after their run finishes, never from step creation while the run is active. Campaign eligibility keeps equivalent evidence. A redirect creates one `event_key`; retrying its write reuses the key, while another actual visit gets a new key. First/last tap counters on the link do not replace the visits or the daily rows. See [ADR 0008](../adr/0008-retain-attribution-evidence.md).

## run-maintenance

One daily job, run in this order. Each step works in bounded batches and can be rerun after a crash. A failed step does not stop the later ones, and the job reports failure after the last step so the queue retries it. The retention for each table is in [growth.md](growth.md).

1. `ensure_monthly_partitions(3)`: create this month and the next three for `audit_log`, `ai_runs` and `tracked_link_visits`. Alert if fewer than two future months exist afterwards.
2. For each finished Asia/Dhaka day after a rollup's `maintenance_watermarks` row, page through `maintenance_store_ids(after, limit)` from a null cursor to an empty page. It includes active, suspended and closing stores; a store remains eligible until permanently purged. Process each store inside `forStore`: link visits into `tracked_link_visit_days`, AI run cost, tokens and counts by purpose into `store_daily_metrics`. Do not use `active_store_ids()` for retention. Upserts make retries safe. Advance the global watermark only after every page and store has finished the day, including stores with no source rows. A failed or unfinished store keeps the watermark unchanged; restart the day's scan from a null cursor on retry. Serialize runs for the same rollup so a stale run cannot overwrite newer progress.

   The job runs at 19:00 UTC (01:00 in Dhaka) and rolls up at most 31 days per run, so a long outage catches up over several nights. A watermark moves by compare-and-set on the value the run read, so a stale run that restarts cannot move it back. With no watermark yet, the first run starts at the first day of the oldest partition. AI runs are stored in `store_daily_metrics` with `dimension` set to the run's purpose and the metrics `ai_runs`, `ai_cost_micro_usd`, `ai_input_tokens` and `ai_output_tokens`.

3. `drop_expired_partitions()`: drop AI run and link visit months older than 13 months. It skips any month past the watermark, so a failed step 2 delays deletion instead of losing data.
4. Archive: export each `audit_log` month older than 24 months to R2 as gzipped JSON lines, check the row count, then drop it as the owner role. Export messages older than 12 months the same way, grouped by conversation and month, whether or not the chat is still active, then delete them in batches. Archives stay in R2 for the life of the store; the store purge deletes them, and a customer's deletion request removes or anonymises that customer's archived messages (D39, [growth.md](growth.md#r2-archives)).
   The audit export reads each store's rows for the month through `forStore`, five thousand at a time, into one gzip stream. It writes one object per store and month at `stores/<storeId>/archive/audit-log/<yyyy-mm>.jsonl.gz` and checks that R2 holds the full object. The drop is the definer function `drop_audit_month(month, expected_rows)`, granted to `dakly_app`: it refuses a month newer than 24 months and any row count that differs from the export, so no caller can drop a recent month or one whose export was short. Exporting messages is part 4 of DB-7, after the purges.
5. Purge in batches of 5,000: published outbox events after 7 days, notifications and `assistant_messages` after 90 days, usage events after 13 months, `store_daily_metrics` rows after 24 months, campaign recipients and workflow steps 372 days after their campaign or run finishes, expired sessions and files.

   Of these, the job so far purges expired `files` and orphan product photos, described next; the other tables in this step wait on later tasks. Webhook payloads are cleared by `purge-webhook-events` (CHN-9), not here. For each store, expired `files` rows go in batches of 500, deleting the R2 object first and the row second, so a crash leaves a row the next run finds again. A file that an import, knowledge item, sender request or data request still points at is left until its owner clears the reference. Objects under `stores/<storeId>/products/` that are more than 24 hours old and have no `files` row are deleted, because an upload is confirmed after the file reaches R2.

6. Account history: call `SELECT public.purge_account_security_events(1000)` as the app role in separate short transactions until it returns fewer than 1,000. Migration 0069 makes the function `SECURITY DEFINER` and grants it to `dakly_app`; it deletes only rows strictly older than two years and rejects limits outside 1–1,000, so the app role cannot use it to remove newer history. It needs no store scan, and no R2 archive is required for account events.

## Send-time and financial gates

Immediately before calling the provider, recheck consent, block status, channel window, campaign state and frozen routing. A queued recipient, or a sending recipient that has not been handed to the provider, may become skipped with its reason; release reserved cost in that same transition. Never label an already accepted or unknown provider outcome skipped. Messenger identity must belong to the frozen sending connection and selected contact; an address alone is insufficient.

Refund jobs consume a reservation made under the common payment-intent lock. Requested/pending capacity stays reserved until a confirmed result; succeeded and recorded-manually refunds consume captured capacity. Reconciliation, failure release and success accounting use the same intent lock and permanent key. Wallet jobs assign the next per-wallet revision under the shared advisory lock and read balances by revision. The schema bounds amounts and enforces uniqueness; these service protocols require concurrency tests before feature release.

Purge transactions use `SET CONSTRAINTS ALL DEFERRED` before dependent deletion and restore `ALL IMMEDIATE` before commit. This lets SET NULL actions finish before their supplemental NO ACTION tenant-reference checks validate final state. Supplemental CASCADE keys match the original action and ordinary cascading deletes do not require deferral. A failed final check rolls back the purge.

## Account security notices

ACC-7 stores encrypted notices durably. Sign-in and TOTP recovery queue `send-security-notice` on `transactional` with `{ noticeId }` after their transaction commits; the handler claims that one notice under the normal lease. The `send-due-security-notices` job scheduler (`packages/core/src/auth/jobs/`) runs every 30 seconds as the safety net, with batches of 20, two-minute leases and retry backoff capped at one hour. Neither payload has `storeId`: these are global account notices. Both handlers call `SecurityNoticesService`, which makes no vendor call under a database lock and acknowledges only its lease. Worker shutdown waits for the active job. Recovery eligibility begins seven days after all required notices are accepted. Duplicate delivery after uncertain vendor outcomes is possible. This does not implement the general DB-2 event relay.

The worker uses the same JSON/Pino configuration as the API. The dispatcher stores the BullMQ job id in an asynchronous context, and the logger adds it to service and vendor metrics; each scheduled run has its own id. Worker errors use the existing sanitized Sentry payload with `jobId`; a failed run is reported and logged once by the dispatcher and retried by BullMQ.

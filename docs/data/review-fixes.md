# PR #6 review corrections

The schema after migration 0014 has 75 tables, 1,011 columns, 295 explicit indexes and 241 foreign keys, including the transitional example table. The ER file is generated from the latest snapshot.

The database review examined commit `c82332157dcdd36167b952a39e301dfca173efef`, every changed schema/contract file, all tables and the drawn ER relationships. The corrections preserve D26–D30. They were first written as a separate migration and then folded into the release 1 migrations (now split by feature, 0003 to 0014), because no database outside development had applied them; there is no data to convert. This page distinguishes database guarantees from contracts for services that have not been implemented.

## Necessity and query review

Each planned table has a named product responsibility. Preserve historical snapshots, workflow versions, financial/stock ledgers and reversible-operation evidence. The example `customers` table is transitional and must be removed through CUS-1 after its data moves to `contacts`. Saved content and repeated tap evidence fill specific gaps; they do not justify adding general duplicate history tables.

No implemented application-level N+1 loop was demonstrated in this schema PR. The measured admin issue is repeated work inside one SQL statement. Future repositories need bounded batch APIs across feature boundaries, stable keyset cursors with unique tie-breakers, correct all-status sorts, tenant-selective consent/search plans and limits on sweeps/provider work. Scale estimates and small fixtures are not throughput guarantees. See [indexes and scale](indexes-and-scale.md).

## Migration and validation scope

The schema starts empty, so no step converts old rows. The constraints added in review (wallet revision, merge operation key, buyer name, scoped variant references, campaign connection, memory checkpoints) hold from the first insert.

Before merging, run the full schema integration suite, contracts/unit tests, `pnpm check`, build, repeated seed and schema no-drift generation, and inspect the populated upgrade results. Report the actual results in the PR. Do not mark the future service criteria above implemented because these checks pass.

PostgreSQL's [definer-function guidance](https://www.postgresql.org/docs/16/sql-createfunction.html#SQL-CREATEFUNCTION-SECURITY), [foreign-key constraints](https://www.postgresql.org/docs/16/ddl-constraints.html) and [partition limitations](https://www.postgresql.org/docs/16/ddl-partitioning.html#DDL-PARTITIONING-DECLARATIVE-LIMITATIONS) explain the database guarantees used here.

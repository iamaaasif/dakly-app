# Features 08 to 13 predevelopment review

Task-mapping findings describe the tracker before this review. The review has added owning rows to [tasks.md](../tasks.md#readiness-review-follow-up), including ORD-9 in M6. Those additions close the missing-row gaps; their implementation, specification and acceptance work remains open. Source line references describe the reviewed baseline.

The main release 1 blockers in these features are conflicting automation rules, incomplete campaign and publishing lifecycles, unresolved admin security and approval storage, and release 1 work without a task. Several prototype criticisms are stale. The screenshots support a narrower set of design gaps than the existing review claims.

This review covers every section of feature docs 08–13, the theme and prototype review, and the relevant glossary, decisions, open questions, data model and task rows. References below use source line numbers from 13 November 2026. A missing acceptance example means the requirement needs a precise observable result; it does not mean the feature must already be implemented.

## Findings to settle before implementation

### F08-01 Campaign pause and failure states are missing from the state model

Priority: high. [Campaigns](../features/09-campaigns-and-automations.md), lines 44, 119, 125–127, 292–294, 323–330, 374 and 394.

The list offers Failed, the design asks for Paused, and business rules require pause for insufficient balance, bad WhatsApp quality and manual intervention. The engineering state machine only has draft, waiting approval, scheduled, sending, sent and cancelled. Quiet hours are described both as deferred sends and recipient skip reasons. These choices determine whether a campaign can finish, resume or refund correctly.

Define campaign and recipient transitions separately, including partial success, waiting for a template, paused reason, resume, cancellation and terminal failure. Specify whether a queued recipient delayed by a daily limit remains queued. Approval freezes the audience and content, but scheduled campaigns can still be edited: define which edits invalidate approval, re-freeze recipients and replace the cost reservation. Define how a template approved after the planned send time is handled and whether an expired offer prevents sending.

Acceptance to add: pause after 40 of 100 sends, resume twice, and send each remaining recipient once; cancel a partially sent campaign and release only unused reservations; edit content after approval and require approval of the new version; a quiet-hours deferral is eventually sent rather than counted as a permanent exclusion.

### F08-02 Workflow frequency, priority and version rules disagree

Priority: high. [Campaigns](../features/09-campaigns-and-automations.md), lines 107, 115, 121, 155, 184–190, 219, 360 and 370–378.

The weekly cap is three messages in CAMP-R3 but two in two later sections. Priority is Transactional, Abandoned, Welcome, Others in one section and Transactional then the rest in engineering. AUTO-R2 says a person reached by two automations receives only the higher priority, while transactional messages elsewhere ignore frequency caps. Two independent order updates must not be lost merely because they share a date.

Version rules also differ: the original section moves people past deleted steps; engineering pins them to an immutable version. Another paragraph changes delays not yet scheduled, and the verified-rules table applies new exit conditions to people already inside. An implementation cannot obey all four literally.

Choose one cap, define whether the weekly cap is across channels or per channel, and distinguish suppression of marketing from required transactional events. Pin normal graph behavior to a version; separately name any safety checks that always use current consent or policy. Specify migration, stop-old-version and pause/resume behavior for waits, manual review and provider retries.

Acceptance to add: two transactional order updates and one marketing send on the same day; two simultaneous jobs claiming the final cap allowance; an old run waiting on a deleted step; changed exit rules during a wait; pause across a scheduled send time and resume after 24 hours. Assert both messages and recorded exit reasons.

### F08-03 Workflow source and action contracts are broader than the delivery plan

Priority: high. [Campaigns](../features/09-campaigns-and-automations.md), lines 74–103, 171–180, 192–227 and 348–362; [open questions](../product/open-questions.md), line 17; [tasks](../tasks.md), lines 157–170.

The source-dependent workflows are hidden in one section and displayed with prerequisites in another. Three recipe lists disagree on membership and timing. The engine requires event waits, ten-way splits, random splits, manual review, tasks for staff, coupons, product recommendations and custom API events, but CAMP-5 and CAMP-6 are broad rows without distinct contracts or acceptance gates for these pieces. Store sync is not built until Q13 is answered; browse tracking is not assigned a task. Random branching is release 1 while automated campaign A/B winner selection is release 2, so those scopes need a clear boundary.

Publish a single release 1 template catalogue with trigger event, required source, classification, channel fallback, timings, exit, owner and task. Define contracts for each action and choose which unsupported ones remain unavailable. Reconcile feature events named workflow, automation and enrollment with the [data model](../product/data-model.md), lines 69–70 and 112.

Acceptance to add: every shipped template validates without unavailable sources; unavailable templates show the same prerequisite policy; duplicate trigger deliveries create one run; a second distinct event for a contact already in the workflow follows the one-active-run rule; every branch has an end and valid typed inputs; actions cannot bypass permissions or approved offer values.

### F08-04 Sending and publishing need an explicit uncertain-result recovery rule

Priority: high. [Content and social](../features/08-content-and-social.md), lines 182–187; [campaigns](../features/09-campaigns-and-automations.md), lines 325–330 and 362.

Three retries for publishing and resuming recipients still queued do not define what happens if the provider accepts a request but Dakly times out before saving success. Retrying such work can publish or charge twice. Instagram container progress also needs durable state before retry. This is a missing domain recovery contract, even where shared job rules require idempotency.

Define the durable operation key, provider id, pending-result state and reconciliation path. A later callback must reconcile with the same send, never produce a second wallet settlement. For social, define cancellation and rescheduling while a job is claimed, retrying only failed targets, and what happens if an account or extension is disconnected before a queued job runs. Define approved caption/media revision handling after edits.

Acceptance to add: provider accepts then connection drops; worker restarts before local success; late success arrives after a timeout; user reschedules a claimed target; Facebook already succeeded while Instagram is retried. Assert one external send per intended target and one charge.

### F08-05 Admin access and audit rules contradict each other

Priority: high. [Admin panel](../features/12-admin-panel.md), lines 92–93, 158–161, 171–179 and 253–269.

The PRD uses an admin database role with cross-store access; engineering explicitly forbids bypassing RLS and requires scoped grants or report functions. The PRD lists six staff roles; engineering lists support, finance, engineering and owner. The audit retention rule says at least seven years with a hash chain; engineering says two years. Engineering also says no shop data without a support grant, although finance and operations need limited shop metadata without an impersonation session.

Keep the non-bypass RLS approach required by engineering and turn it into one explicit permission matrix: cross-store metadata reports, financial domain actions, shop content via approved support grant, and exceptional break-glass access. Reconcile roles and retention with the repository security rules. Distinguish an audit of an attempted denied action from the transactional audit of a successful mutation. Do not leave the feature marked as having no open questions while these choices remain unresolved.

Acceptance to add: each role receives only permitted report fields; a revoked or expired grant denies API access as well as closing the UI; a finance action does not require broad chat access; cross-store report functions cannot expose bodies or credentials; conflict-of-interest checks apply to support and financial actions.

### F08-06 Mandatory two-person approval has no settled persistence contract

Priority: high. [Admin panel](../features/12-admin-panel.md), lines 161, 173, 187–194, 224, 255 and 269; [open questions](../product/open-questions.md), line 15.

Store deletion, large refunds or credits, bulk price changes, global AI pause and break-glass require a second person. Engineering names a different set, adding plan overrides, and lists staff approvals as deferred by the pending schema review. There is no stated substitute for durable approval requests. This is required release 1 behavior, not optional scaffolding.

Settle the action list and thresholds and provide storage for immutable proposed payload, requester, eligible approver, expiry, rejection and execution result. Prevent approval by the requester, replay, changing the payload after approval, and splitting actions to evade thresholds. An emergency global stop also needs an explicit policy because the current document simultaneously promises a one-minute switch and permits waiting 24 hours for approval.

Acceptance to add: self-approval fails; a request expires without any gateway call; changing the amount requires a new request; concurrent approvals execute once; a timed-out refund is reconciled before retry; emergency stop behavior matches the chosen approval policy.

### F08-07 Release 1 commitments are not all mapped to tasks

Priority: high. [Tasks](../tasks.md), lines 143–180; [content and social](../features/08-content-and-social.md), lines 109–114; [dashboard](../features/10-dashboard-and-notifications.md), lines 147–150; [analytics](../features/11-analytics.md), lines 140–145; [admin panel](../features/12-admin-panel.md), lines 33–47 and 249.

The tracker covers the major screens but does not explicitly assign weekly content planning, festival suggestions, product photo tools, shared ideas, WhatsApp digests, notification preferences and push, profit reporting, the AI agent report, abuse handling, company metrics, announcements, data requests or staff account management. Some may fit broad existing tasks, but that relationship and its acceptance boundary are not stated. Five admin tasks do not visibly cover all release 1 admin commitments.

Map each release 1 row to an owning task and acceptance section, or record a scope decision deferring it. Separate the many independent workflow contracts within CAMP-5 and CAMP-6 so the template-first release path has a measurable completion gate. Do not treat a feature heading or screenshot as a delivery task.

### F08-08 POS CSV is release 1 but lives under a blanket prohibition

Priority: high. [Decisions](../product/decisions.md), lines 7 and 12; [physical shop](../features/13-physical-shop.md), lines 11, 17, 32, 101–108 and 208–211; [analytics](../features/11-analytics.md), line 21.

D6 explicitly puts POS CSV in release 1, but feature 13 says to build none of the page in release 1. Its POS CSV section still says release 1, and the tracker has no POS import task. This is a scope and ownership conflict, not a reason to bring the whole counter product forward.

Extract or clearly exempt the release 1 POS import contract and assign a task. Define receipt grouping because files may contain several item rows for one receipt: the current rule skips duplicate receipt number plus branch, which would drop legitimate additional items if applied per row. The required amount column is absent from the listed template columns. Define corrections, historical order dates, stock effects, consent proof and re-upload behavior.

Acceptance to add: one receipt with three line items becomes one order; another store can use the same receipt number; re-upload does not duplicate it; valid rows and rejected rows reconcile with totals; a historical POS import does not trigger current transactional messages unless explicitly requested.

### F08-09 Attribution rules disagree and do not cover delayed evidence

Priority: high. [Analytics](../features/11-analytics.md), lines 59–68, 97–103, 118, 128 and 205; [glossary](../product/glossary.md), lines 85–87 and 100–109.

Engineering removes returned orders from attribution, while the glossary and acceptance example retain the order count and subtract returned money. Engineering omits delivered SMS from eligible touches. ANA-R2 permits only the Owner to change the window, but the permissions paragraph also permits Admin. The glossary takes precedence for metric definitions; the feature should state the same rule throughout.

Attribution is described at order creation and window change, but a read or delivery callback can arrive after the order while carrying an earlier event time. Define reprocessing for delayed callbacks, customer merges, returns, refunds, excluded contacts and historical imports. Define whether changing the window restates every visible period and how failure or a second window change during recalculation is handled. The social tracked-link contract also needs a way to associate an anonymous click with a later identified customer without attributing every click to one recipient.

Acceptance to add: read callback arrives after an order but read time precedes it; half an order is returned; merged identities do not credit the order twice; delivered SMS receives credit; a link bot does not create a customer conversion; concurrent window recalculations expose one coherent version of the reports.

### F08-10 Funnel and company metrics still lack computable definitions

Priority: medium. [Analytics](../features/11-analytics.md), lines 78–84 and 140–145; [glossary](../product/glossary.md), lines 105–112; [admin panel](../features/12-admin-panel.md), lines 139–145 and 227.

The funnel mixes messages, unique people and orders while promising a percentage of the preceding step. An order may be attributed to a delivered SMS without a tap, and one person may place several orders. Ordered can exceed Tapped without an error. The glossary's messages-sent wording says both each SMS part counts and not per part. Company MRR, churn and activation are said to come from the glossary but are not defined there. Summing active subscriptions does not by itself define monthly value for yearly plans, trials, discounts, VAT, refunds or currencies.

Choose the entity and denominator for every funnel step and explain when it is a set of measures rather than a strictly shrinking funnel. Define reporting periods for sends versus orders, campaign status-label precedence and low-data baselines. Add a company metrics glossary and cost-basis rules before promising a profit view. Resolve the release 1 columnar-store statement against launch Postgres summaries and the later ClickHouse approach.

Acceptance to add: two orders after one delivered SMS with no click; repeat messages to one person; SMS with multiple parts; yearly discounted subscription and refund; empty median baseline; product cost unknown or changed after sale.

### F08-11 Notification recipients, deduplication and delivery conflict

Priority: high. [Dashboard](../features/10-dashboard-and-notifications.md), lines 58–73, 114–115, 147–149 and 243–247.

The schema working assumption is one row per user, but the dedupe key is unique per store. Those rules cannot create the same notification for two users unless the recipient is included in uniqueness or a separate event identity is introduced. Done and Undo are not defined as personal or shared. A condition can expire after seven days but later recur; current dedupe wording only explains creation until done.

NOTIF-R2 escalates every unopened Fix now card by push or SMS, whereas engineering permits SMS, WhatsApp or email only for billing, credentials and security. The daily WhatsApp digest is another exception that needs a delivery, consent and billing contract. Choose the recipients, per-user state, dedupe scope, reopening policy, expiry, snooze and escalation policy, including whether opening by one owner cancels escalation for another.

Acceptance to add: two eligible members each receive one card; a repeated trigger adds no duplicates; one member marking Done has the chosen effect on the other; condition clears and recurs; consent or permissions change before delivery; unavailable or unsubscribed push has a defined fallback; digest retry does not double charge.

### F08-12 Ask Dakly needs conversation storage and stale-permission behavior

Priority: medium. [Dashboard](../features/10-dashboard-and-notifications.md), lines 77–113, 126 and 249–272.

Read-only tools, source disclosure and approval navigation are useful constraints. The feature promises private per-user history for 90 days, but its data section lists only notifications and push subscriptions. It does not define what happens to saved answers after a role loses access, after a store switch or after referenced customer deletion. One-unit answers and three-unit content drafts need a failure, cancellation and retry charging rule.

Define where conversations live, their store and user scope, retention, deletion and authorization at read time. Define typed action payloads with permission checks on the destination screen so an old prepared campaign cannot bypass current reach, price or consent checks. Keep the factual count separate from an estimated sample.

Acceptance to add: a masked-phone role receives no full phone in tools, text, history or action payloads; user A cannot read user B's conversation; changing stores cannot reuse the old context; timeout or retry consumes the intended number of credits; an action prepared yesterday is reviewed against today's data.

### F08-13 Social collaboration and release additions need lifecycle rules

Priority: medium. [Content and social](../features/08-content-and-social.md), lines 39–45, 76–79, 109–114, 183 and 206.

Drafts are private to their creator except for Owner/Admin, but the release 1 addition promises shared team drafts and an idea board. The library has save, search and reuse without ownership, deletion or retention rules. Weekly planning, festival suggestions and product photo tools have no input limits, usage prices or acceptance examples. Saving an AI caption moves to waiting approval, but it is not clear whether approval covers the post or each target and whether editing media invalidates it. The feature lists only social permissions although Content Studio is core and Social Auto Post is an extension.

Define separate content and publishing permissions, private versus shared saved content, approval revision scope and extension-off behavior. Give each release 1 addition an explicit task or deferral. Define how brand changes affect saved content and how blocked or unavailable generation is charged.

Acceptance to add: Marketer cannot read another creator's private draft; Owner can; an explicitly shared idea is visible to permitted teammates; approved caption changed by an editing tool returns to review; Content Studio works when Social Auto Post is off; a weekly batch is approved item by item or by an explicit whole-batch action.

### F08-14 Theme contrast guidance would produce inaccessible controls

Priority: high before WEB-1. [Theme](../design/theme.md), lines 16–20, 37 and 43–53; [accessibility rules](../rules/frontend-accessibility.md), rule 8.

The theme permits white text on the primary orange at 14 px semibold and calls 18 px text large. Calculating the supplied colors gives white on `#F06306` a ratio of 3.2345:1; `#A79D96` placeholders on white give 2.6561:1. These fail the normal-text minimum of 4.5:1. The large-text exception is 18 point regular or 14 point bold, approximately 24 px or 18.7 px, not 14 px semibold. Placeholders are included in the text contrast requirement. See [W3C contrast minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html).

Choose a passing primary text/background pair for normal buttons and a separate passing placeholder token. The existing hover orange on white calculates to 4.7576:1 and could be evaluated as one option. Resolve `text-lg` weight 650 against the stated allowed weights of 400, 500, 600 and 700.

Acceptance to add: all normal button labels and active placeholders meet 4.5:1 using the actual CSS values; light-background link text passes too; Bengali text is readable at each size and line-height; keyboard focus remains visible and is not conveyed only by color.

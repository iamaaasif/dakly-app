# Writing: docs, comments, UI copy, commits

Everything in this repo should read as if a careful person wrote it for a colleague. AI tools are welcome for drafts; their marks are removed before the PR. Sources: the [Google developer documentation style guide](https://developers.google.com/style), [plainlanguage.gov](https://www.plainlanguage.gov/guidelines/), and [Novu's contributing rules](https://github.com/novuhq/novu/blob/next/CONTRIBUTING.md).

## Rules

1. Short sentences. Common words. Active voice: "The job sends the message", not "The message is sent by the job".
2. Say the thing. Lead with the answer or the rule, then the reason.
3. Use the glossary's words (Store, Contact, Chat, Order, Parcel). Do not invent synonyms.
4. Numbers and examples beat adjectives: "loads in under 2 seconds for 50,000 customers", not "fast and scalable".
5. One example per rule. No shouting in capitals, no "IMPORTANT", no "CRITICAL".
6. No emoji in docs, code, comments, commit messages or UI copy.
7. No banners or footers that say a tool wrote something. Authorship is in git.
8. No filler. `pnpm lint:docs` flags these words and phrases in Markdown and in code comments:

| Avoid                                                                         | Write instead                   |
| ----------------------------------------------------------------------------- | ------------------------------- |
| delve, leverage, utilize, facilitate                                          | look at, use, help              |
| seamless, robust, powerful, cutting-edge, state-of-the-art, best-in-class     | say what it does, with a number |
| comprehensive, holistic, end-to-end solution                                  | name what it covers             |
| "It's important to note that", "It is worth noting", "Note that"              | the fact itself                 |
| "In today's fast-paced world", "In conclusion", "Let's dive in"               | nothing                         |
| "This ensures that", "in order to"                                            | "so", "to"                      |
| "Generated by", "As an AI", "I hope this helps"                               | nothing                         |
| navigate the complexities, unlock, empower, elevate, streamline, game-changer | the plain verb                  |

9. Headings in sentence case. Lists only for real lists; reasoning goes in sentences.
10. Docs say what is true now. Plans go in [tasks.md](../tasks.md); history is in git.

## Code comments

Covered in [naming-and-comments.md](naming-and-comments.md): explain why, one to three lines, no JSDoc on obvious functions, no commented-out code.

## UI copy

- Short and specific: "Send 103 messages for ৳927", not "Proceed with campaign dispatch".
- Say what happened and what to do: "bKash is having problems. Customers can still pay with Nagad or card."
- Write for a shop owner, not an engineer: no "sync", "token", "webhook", "API" on screens unless the screen is for developers.

## Commit messages and PRs

- Conventional prefix and a plain summary under 72 characters: `feat: confirm orders from a WhatsApp reply`.
- The body says why, in sentences. The PR template's sections, filled in honestly.
